# 方法学更正 + 回溯复核：探针退出码 ≠ 实例存活

- 作者：**verifier**；采集：本地 19:47–19:49（UTC 11:47–11:49）
- 触发：captain 转达 audio-engine 的判别实验：**探针的非零退出码（`0xC0000409`）是 Node 收尾关闭共享 WebSocket 时的 libuv 断言，与 Electron 应用无关**
- 本文做两件事：**(1)** 采纳该口径并固化判据；**(2)** **回溯复核**我此前所有"实例死亡"记录，逐条按"当时的实际依据"重新裁定（含对**我自己的过度主张**的更正）

## §1 采纳的判据（三查解耦，替代"看退出码"）

| 问题 | 正确判据 | **不得**使用 |
|---|---|---|
| 探针成功与否 | 落盘 JSON 是否**完整**（含 `verdict`/`assertions` 等判定字段） | 探针退出码（`0xC0000409` 是 libuv 收尾噪声） |
| 实例是否存活 | ① `CDP /json/version` 可达；② `electron` 进程数；③ `5173` 监听 | 探针退出码；"没看到日志"（见 §4） |
| 本项是否通过 | JSON 完整 **且** 实例存活 → **通过** | "探针中断"（若上两项均成立，就不是中断） |

**依据（audio-engine 的判别实验，我采纳为上游事实）**：不跑探针实例存活 40 s；跑完 23 s 的 acceptance 探针、结果完整落盘后**实例仍 CDP UP、electron=6**；而探针自身退出码为 `0xC0000409`。
⇒ 该退出码**不能**作为应用崩溃的证据。**`exit 0` 仍可作正向旁证，但它不是判据。**

## §3 对"进程级死亡"开放项的影响

### §3.0 captain 的并列裁定（采纳，优先级最高）

**两类记录并列保留、互不取消** —— 我的"实例在取证期间消失"与 audio-engine 的"不跑探针 40 s 存活 / 跑完 23 s 探针后 CDP 仍 UP、electron=6"**同时成立**，任何一方的反证都不推翻另一方。
- **探针退出码对双方都是噪声**：对 audio-engine 的 `0xC0000409` 是 libuv 收尾断言；对我这两次（`ECONNREFUSED 9222` / `evaluate timed out`）也**不是** `0xC0000409`，因此**不得**用后者去解释前者。
- 结论：**「dev 实例在取证期间消失」= 环境/基础设施现象（未定性）**，不写成产品缺陷、也不写成"已解释"。
- **三件套必须同时记录**：`探针退出码` + `electron 进程数` + `应用日志尾部的 [error]` 行。

- **加强**：`0xC0000409` **不再**作为应用死亡的任何证据 ⇒ "重负载探针期间致死"这一描述里，**探针侧**的部分完全由 libuv 收尾噪声解释；
- **仍未定性**：仅有 E、F 两处支持"应用/作业树确实消失"，而两者的成因（作业树回收 = 我此前已裁定的环境/基础设施）都与探针退出码无关；
- ⇒ 维持 captain 口径：**进程级死亡未定性，唯一判定台是 t9 打包态长跑**（不嵌套探针作业、不经 vite、`Start-Process` 独立进程组 + 记录 PID）。

## §4 伴随现象（不得写成成因）

- 「**崩溃时 mock 更新服务 `8888` 不通**」记为**伴随现象**：`updateURL` 指向 `http://127.0.0.1:8888/`（dev 日志中大多数 boot 打印 `update feed=http://127.0.0.1:8888/`），`8888` 未运行时 `checkUpdate` 走 catch + warn（**正常容错**）。
- 与已采纳的定位一致：**缺键缺陷真实存在，但 `trim` 异常只走 logging 守卫、不杀进程**（打包态 7 次修复前崩溃见 `LOG-ANALYSIS-dev-vs-packaged.md` §6；dev 态全天 `uncaughtException`=0）。
- **另一条同类更正**（见 `LOG-ANALYSIS-dev-vs-packaged.md` §2）：**应用日志无法判定启动早期即退** —— `[main] window loaded` 是 `console.log`，只进 stdout。所以"没写日志"同样不能当作死亡证据。
